# Type C (Scientific & Literature Agents) & Type D (Benchmark-Driven Deep Research Agents) — Deep Mechanism & Failure Analysis

**Survey Date:** 2026-11-09
**Scope:** 10 Open-Source Repositories across Scientific Literature Synthesis/Discovery (Type C) and Benchmark-Driven Long-Horizon Research Agents (Type D).
**Verification Standard:** All architectural claims, prompt templates, hyperparameters, benchmark scores, and failure modes below are verified directly from repository source code, configuration files, and GitHub Issues via the GitHub API (`gh`).

---

## 1. Executive Summary & Repository Snapshot

Type C (Scientific & Literature Agents) and Type D (Benchmark-Driven Deep Research Agents) represent the two highest-rigor poles of the open-source research agent ecosystem:
- **Type C systems** (`stanford-oval/storm`, `Future-House/paper-qa`, `SakanaAI/AI-Scientist` v1/v2, `stanford-oval/WikiChat`, `HKUDS/Auto-Deep-Research`) optimize for **epistemic fidelity, multi-perspective coverage, atomic claim verification, and citation precision** over long-form outputs.
- **Type D systems** (`Alibaba-NLP/DeepResearch`, `MiroMindAI/MiroThinker`, `RUC-NLPIR/WebThinker`, `TIGER-AI-Lab/OpenResearcher`) optimize for **long-horizon multi-step reasoning (100–600 tool turns) and context window survival** on adversarial QA benchmarks (`BrowseComp`, `BrowseComp-Plus`, `GAIA`, `HLE`, `xbench-DeepSearch`).

## 2. Type C: Scientific & Literature Agents — Deep Inspection

### 2.1 `stanford-oval/storm` (STORM & Co-STORM)

- **Repository & Papers:** [`stanford-oval/storm`](https://github.com/stanford-oval/storm) — accessed 2026-11-09; STORM (Shao et al., NAACL 2024, [`arXiv:2402.14207`](https://arxiv.org/abs/2402.14207) — accessed 2026-11-09); Co-STORM (Jiang et al., EMNLP 2024, [`arXiv:2408.15232`](https://arxiv.org/abs/2408.15232) — accessed 2026-11-09).
- **Exact Mechanism for Planning & Perspective Discovery:**
  - Implemented in [`knowledge_storm/storm_wiki/modules/persona_generator.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/storm_wiki/modules/persona_generator.py) — accessed 2026-11-09.
  - Instead of asking an LLM to brainstorm perspectives in a vacuum, `CreateWriterWithPersona` first calls `FindRelatedTopic` to identify existing Wikipedia subjects in the same domain, fetches their live URLs via the retrieval module (`rm`), and parses their H2–H6 Table of Contents using `BeautifulSoup` (`get_wiki_page_title_and_toc`).
  - `GenPersona` then takes those structural examples and outputs $N$ numbered personas (`1.Short summary of persona 1: description...`), always prepending `"Basic fact writer: Basic fact writer focusing on broadly covering the basic facts about the topic"` as Persona 0.
- **Knowledge Curation & Multi-Turn Questioning:**
  - Implemented in [`knowledge_storm/storm_wiki/modules/knowledge_curation.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/storm_wiki/modules/knowledge_curation.py) — accessed 2026-11-09.
  - Runs parallel `ConvSimulator` threads via `ThreadPoolExecutor` (one per persona). In each turn, `WikiWriter` generates a single question (`AskQuestionWithPersona`) or outputs `"Thank you so much for your help!"` when satisfied (`max_turn` cap).
  - `TopicExpert` decomposes the question into up to `max_search_queries_per_turn` search queries (`QuestionToQuery`), executes retrieval excluding Wikipedia URLs, keeps only the first snippet per result (`r.snippets[:1]`), truncates total snippet context to **1,000 words**, and synthesizes an inline-cited answer (`AnswerQuestion`).
- **Context Window Management (Preventing Context Rot):**
  - **Sliding Turn Masking in `WikiWriter.forward`** ([`knowledge_curation.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/storm_wiki/modules/knowledge_curation.py) — accessed 2026-11-09): To prevent earlier answers from exhausting the prompt and causing repetitive questions, STORM keeps full question-and-answer text (with bracketed citations stripped via `ArticleTextProcessing.remove_citations`) **only for the last 4 turns** (`dialogue_turns[-4:]`). For all older turns (`dialogue_turns[:-4]`), it retains the writer's question so the model knows what was already asked, but replaces the expert's answer with the literal string: `"Omit the answer here due to space limit."` The combined conversation string is then hard-capped at **2,500 words** (`limit_word_count_preserve_newline(conv, 2500)`).
  - **Two-Stage Outline Synthesis** ([`outline_generation.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/storm_wiki/modules/outline_generation.py) — accessed 2026-11-09): First generates a zero-shot parametric outline (`WritePageOutline` -> `old_outline`), then passes `old_outline` + the concatenated persona dialogues (hard-capped at **5,000 words**) to `WritePageOutlineFromConv` to produce the grounded hierarchical outline.
  - **Section-Isolated Parallel Drafting** ([`article_generation.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/storm_wiki/modules/article_generation.py) — accessed 2026-11-09): Each top-level section is drafted independently in parallel via `ConvToSection`. Rather than feeding the full conversation history into the writer, `StormInformationTable.retrieve_information` embeds the section's sub-outline queries (`paraphrase-MiniLM-L6-v2`), retrieves the top-$k$ raw snippets (`max_words=1500`), and re-indexes them `[1]...[n]` per section before remapping indices globally.
  - **Co-STORM Dynamic Mind-Map (`KnowledgeBase`)** ([`knowledge_storm/collaborative_storm/engine.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/collaborative_storm/engine.py) & [`information_insertion_module.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/collaborative_storm/modules/information_insertion_module.py) — accessed 2026-11-09): Replaces flat transcripts with a hierarchical tree of `KnowledgeNode` objects. `InsertInformationModule` (`LayerByLayerIntentPlacement`) traverses the tree top-down using actions (`insert`, `step: [child_name]`, `create: [new_child_name]`) to file every retrieved snippet under a specific conceptual node, automatically expanding any node whose snippet count exceeds `expand_node_threshold`. The `Moderator` and experts read a compact `#`-heading summary (`KnowledgeBaseSummaryModule`) rather than raw transcripts.
- **Cost Tiering:**
  - [`engine.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/storm_wiki/engine.py) — accessed 2026-11-09 explicitly tiers models: `conv_simulator_lm` (`gpt-4o-mini`, `max_tokens=500`), `question_asker_lm` (`gpt-4o-mini`, `max_tokens=500`), `outline_gen_lm` (`gpt-4-0125-preview`, `max_tokens=400`), and `article_gen_lm` / `article_polish_lm` (`gpt-4o`, `max_tokens=700` / `4000`).
- **Known Failure Modes & GitHub Issues:**
  1. **Benchmark Metric Inflation Bug ([Issue #572](https://github.com/stanford-oval/storm/issues/572) — accessed 2026-11-09):** In `eval/metrics.py` (`heading_entity_recall` and `article_entity_recall` on the `NAACL-2024-code-backup` branch), when ground-truth `golden_entities` is empty (which happens frequently on generic Wikipedia headings like `"History"` or `"Overview"`), the function executes `if len(g) == 0: return 1` without checking whether predicted entities are also empty. This awards a vacuous perfect recall score of `1.0`, systematically inflating published `Heading Entity Recall` benchmarks.
  2. **Silent Citation-Dropping Regex Bug ([Issue #573](https://github.com/stanford-oval/storm/issues/573) — accessed 2026-11-09):** In `ArticleTextProcessing.remove_uncompleted_sentences_with_citations` (`knowledge_storm/utils.py`), the regex `r"([.!?])\s*(\[\d+\])?\s*"` matches at most one bracketed citation at the end of a sentence. When the LLM writes multi-source sentences like `"A fact.[1][2] Unfinished"`, the post-processor truncates at `[1]` and **silently deletes `[2]`** (and all subsequent citations on that sentence).
  3. **Markdown Heading Parser Corruption ([Issue #581](https://github.com/stanford-oval/storm/issues/581) — accessed 2026-11-09):** `ArticleTextProcessing.parse_article_into_dict` uses `line.count("#")` everywhere in the line to determine heading depth and `line.strip("# ")` to extract the title. Consequently, a top-level section titled `# C#` is misparsed as a level-2 heading titled `C` and nested inside the preceding section.
  4. **Zero-Result Crash ([Issue #547](https://github.com/stanford-oval/storm/issues/547) — accessed 2026-11-09):** When a niche topic or strict filter returns zero search results, `StormInformationTable.prepare_table_for_retrieval` leaves `self.encoded_snippets` empty and `cosine_similarity` crashes with a `ValueError` on a 1D array.
  5. **Long-Term Knowledge Base Duplication ([Issue #409](https://github.com/stanford-oval/storm/issues/409) — accessed 2026-11-09):** Users curating persistent knowledge bases across sessions report duplicate/conflicting entries and lack of cross-session contradiction reconciliation.

### 2.2 `Future-House/paper-qa` (PaperQA2)

- **Repository & Paper:** [`Future-House/paper-qa`](https://github.com/Future-House/paper-qa) — accessed 2026-11-09; Skarlinski et al., *Language agents achieve superhuman synthesis of scientific knowledge* (PaperQA2, [`arXiv:2409.13740`](https://arxiv.org/abs/2409.13740) — accessed 2026-11-09).
- **Exact Mechanism for Planning & Agentic Search:**
  - Implemented in [`src/paperqa/agents/env.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/agents/env.py) and [`src/paperqa/agents/tools.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/agents/tools.py) — accessed 2026-11-09.
  - Uses an `aviary` `ToolSelector` agent loop with 5 core tools: `PaperSearch` (queries full-text index with keyword query + optional `min_year`/`max_year`), `GatherEvidence` (runs RCS over current index for a specific question), `GenerateAnswer` (synthesizes answer from top-ranked contexts), `Reset` (clears gathered contexts if off-track), and `Complete` (declares `has_successful_answer: bool`, required before termination unless `agent_type="fake"` deterministic `search -> gather_evidence -> gen_answer` pipeline is used in [`fast.json`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/configs/fast.json) — accessed 2026-11-09).
- **Evidence Grading — Ranking & Contextual Summarization (RCS):**
  - Implemented in [`src/paperqa/docs.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/docs.py) (`Docs.aget_evidence`) and [`src/paperqa/core.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/core.py) (`_map_fxn_summary`) — accessed 2026-11-09.
  - **Step 1 (Hybrid Chunk Retrieval + MMR):** Documents are chunked into `chunk_chars=5000–7000` (`overlap=250`, or `1750`/`100` in [`wikicrow.json`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/configs/wikicrow.json) — accessed 2026-11-09) and embedded with `hybrid-text-embedding-3-small` (combining dense OpenAI embeddings with a 256-dim sparse modulo token vector). Top `evidence_k` chunks (`10` default, `15` in `high_quality.json`, `25` in `wikicrow.json`, `30` in `contracrow.json`) are selected via Maximal Marginal Relevance (MMR).
  - **Step 2 (Concurrent Contextual Summarization & 0–10 Scoring):** Never feeds raw PDF chunks to the final synthesis LLM. Instead, `summary_llm` processes all `evidence_k` chunks concurrently using `summary_json_system_prompt` ([`src/paperqa/prompts.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/prompts.py) — accessed 2026-11-09):
    > *"Provide a summary of the relevant information that could help answer the question based on the excerpt. Stay detailed; report specific numbers, equations, or direct quotes (marked with quotation marks)... Respond with the following JSON format: `{"summary": "...", "relevance_score": "..."}` where `relevance_score` is an integer from 0 to 10."*
  - **Step 3 (Hard Cutoff & Top-$N$ Pruning):** Chunks with `score <= evidence_relevance_score_cutoff` (`1`) are discarded. Remaining `Context` summaries are sorted by `score` descending and truncated to `answer_max_sources` (`5` default, `10` in `high_quality`, `12` in `wikicrow`, `15` in `contracrow`).
- **Source Quality Metadata & Retraction Verification:**
  - Implemented in [`src/paperqa/clients/`](https://github.com/Future-House/paper-qa/tree/main/src/paperqa/clients) (`crossref.py`, `semantic_scholar.py`, `openalex.py`, `journal_quality.py`, `retractions.py`) — accessed 2026-11-09.
  - At ingestion time, `MetadataPostProcessor` queries Crossref, Semantic Scholar, OpenAlex, journal quality tables, and a Retraction Watch database to append provenance directly into the `citation` string passed to both the RCS and QA prompts (`CONTEXT_INNER_PROMPT = "{name}: {text}\nFrom {citation}"`), e.g., *"This article has 243 citations and is from a domain leading peer-reviewed journal."*
- **Citation Verification & Hallucination Prevention:**
  - Implemented in [`src/paperqa/prompts.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/prompts.py) (`CITATION_KEY_CONSTRAINTS`) and [`src/paperqa/core.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/core.py) (`strip_citations`) — accessed 2026-11-09.
  - Every `Context` receives a deterministic hash key like `pqac-d79ef6fa`. Before summarizing or answering, `strip_citations` strips existing academic citations (`[1]`, `(Smith et al., 2020)`) from the source text so the LLM cannot confuse secondary citations inside a paper with primary context keys. Furthermore, when iterating on a `prior_answer` (`answer_iteration_prompt_template`), the prompt enforces: *"Do not reuse any citation keys from the prior answer which are not also present in the above context."*
- **Contradiction Detection (`ContraCrow`):**
  - Configured in [`src/paperqa/configs/contracrow.json`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/configs/contracrow.json) — accessed 2026-11-09.
  - Evaluates whether two scientific claims contradict using 30 retrieved contexts (`answer_max_sources=15`) and outputs `<reasoning>` followed by an 11-point `<label>` scale: `explicit contradiction`, `strong contradiction`, `contradiction`, `nuanced contradiction`, `possibly a contradiction`, `lack of evidence`, `possibly an agreement`, `nuanced agreement`, `agreement`, `strong agreement`, `explicit agreement`.
- **Published Benchmarks & Caveats:**
  - PaperQA2 ([`arXiv:2409.13740`](https://arxiv.org/abs/2409.13740) — accessed 2026-11-09) reports outperforming PhD/postdoc human baselines on **LitQA2** (precision/recall on multiple-choice retrieval QA), **WikiCrow** (zero-contradiction factual accuracy on Wikipedia-style gene articles), and **ContraCrow** (detecting paper contradictions). Train/eval splits are published in [`docs/2024-10-16_litqa2-splits.json5`](https://github.com/Future-House/paper-qa/blob/main/docs/2024-10-16_litqa2-splits.json5) — accessed 2026-11-09. However, the repo's README FAQ explicitly notes that FutureHouse's internal benchmark harness uses proprietary full-text paper APIs and citation traversal tools that are not bundled in the open-source repo.
- **Known Failure Modes & GitHub Issues:**
  1. **Silent Permanent Exclusion of Transiently Failed Papers ([Issue #1355](https://github.com/Future-House/paper-qa/issues/1355) — accessed 2026-11-09):** In `SearchIndex.filecheck`, files that previously failed ingestion (e.g., due to a transient `429 Too Many Requests` from Crossref/Semantic Scholar) are recorded as `"ERROR"` in `index_files` and **silently skipped on all subsequent runs** without warning or retry, permanently dropping papers from the corpus.
  2. **Insecure Pickle Deserialization in Index Storage ([Issue #1325](https://github.com/Future-House/paper-qa/issues/1325) & [Issue #1227](https://github.com/Future-House/paper-qa/issues/1227) — accessed 2026-11-09):** Persisted search indices default to `SearchDocumentStorage.PICKLE_COMPRESSED`, which calls `pickle.loads(zlib.decompress(data))` (CWE-502 arbitrary code execution if loading shared indices) and breaks across `paper-qa` version upgrades when Pydantic model fields change.
  3. **Aggressive Raw-Chunk Dropping ([Issue #1253](https://github.com/Future-House/paper-qa/issues/1253) — accessed 2026-11-09):** Because `core.py` drops embeddings and relies on `Context.context` summaries rather than raw chunks during `GenerateAnswer`, if `summary_llm` omits a detail during RCS, the synthesis model has zero access to the underlying passage.

### 2.3 `SakanaAI/AI-Scientist` (v1) & `SakanaAI/AI-Scientist-v2`

- **Repositories & Papers:** [`SakanaAI/AI-Scientist`](https://github.com/SakanaAI/AI-Scientist) — accessed 2026-11-09 (Lu et al., [`arXiv:2408.06292`](https://arxiv.org/abs/2408.06292) — accessed 2026-11-09) and [`SakanaAI/AI-Scientist-v2`](https://github.com/SakanaAI/AI-Scientist-v2) — accessed 2026-11-09 (Yamada et al., [`arXiv:2504.08066`](https://arxiv.org/abs/2504.08066) / [`pub.sakana.ai/ai-scientist-v2/paper`](https://pub.sakana.ai/ai-scientist-v2/paper/paper.pdf) — accessed 2026-11-09).
- **Exact Mechanisms:**
  - **Hypothesis Generation & Novelty Checking:**
    - *v1* ([`ai_scientist/generate_ideas.py`](https://github.com/SakanaAI/AI-Scientist/blob/main/ai_scientist/generate_ideas.py) — accessed 2026-11-09): Requires a human-authored `experiment.py` baseline and `seed_ideas.json`. Generates JSON hypotheses with self-scored `Interestingness`, `Feasibility`, and `Novelty` (1–10) over `num_reflections=5` rounds, followed by a post-hoc Semantic Scholar loop (`check_idea_novelty`, `max_num_iterations=10`) that makes a binary `Novel` decision.
    - *v2* ([`ai_scientist/perform_ideation_temp_free.py`](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/ai_scientist/perform_ideation_temp_free.py) — accessed 2026-11-09): Removes code templates; takes a short Markdown workshop prompt and interleaves `SearchSemanticScholar` tool calls inside the 5 reflection rounds before calling `FinalizeIdea` (`Short Hypothesis`, `Related Work`, `Abstract`, `Experiments`, `Risk Factors and Limitations`).
  - **Experimental Execution (Linear Loop vs. 4-Stage Best-First Tree Search):**
    - *v1* ([`ai_scientist/perform_experiments.py`](https://github.com/SakanaAI/AI-Scientist/blob/main/ai_scientist/perform_experiments.py) — accessed 2026-11-09): Linearly invokes `aider` (`coder.run`) up to `MAX_RUNS=5` (`MAX_ITERS=4` retries per run) to edit `experiment.py` and `plot.py`, logging textual notes to `notes.txt`.
    - *v2* ([`ai_scientist/treesearch/agent_manager.py`](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/ai_scientist/treesearch/agent_manager.py) & [`bfts_config.yaml`](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/bfts_config.yaml) — accessed 2026-11-09): Uses progressive 4-stage Best-First Tree Search (BFTS) across `num_workers: 4` parallel processes and `num_seeds: 3` multi-seed validation:
      1. **Stage 1 (`initial_implementation`, max 20 iters, 3 drafts):** Generates a working baseline implementation from scratch (`max_debug_depth: 3`, `debug_prob: 0.5`).
      2. **Stage 2 (`baseline_tuning`, max 12 iters):** Tunes hyperparameters and adds datasets.
      3. **Stage 3 (`creative_research`, max 12 iters):** Tests the core novel hypothesis and architectural modifications.
      4. **Stage 4 (`ablation_studies`, max 18 iters):** Systematically ablates components to prove causal contribution.
  - **Context Management (`log_summarization.py`):**
    - Implemented in [`ai_scientist/treesearch/log_summarization.py`](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/ai_scientist/treesearch/log_summarization.py) — accessed 2026-11-09. Each BFTS stage records a tree `Journal` of `Node` objects (code, plan, metric, VLM plot analysis). After all stages finish, `overall_summarize` runs `get_stage_summary` (`report_summarizer_prompt`) on best/child nodes and `stage_aggregate_prompt` to emit 4 JSON files (`draft_summary.json`, `baseline_summary.json`, `research_summary.json`, `ablation_summary.json`) for the writeup agent.
  - **Citation Verification & LaTeX Writeup:**
    - Implemented in [`ai_scientist/perform_writeup.py`](https://github.com/SakanaAI/AI-Scientist/blob/main/ai_scientist/perform_writeup.py) (v1) and [`ai_scientist/perform_icbinb_writeup.py`](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/ai_scientist/perform_icbinb_writeup.py) (v2) — accessed 2026-11-09. Queries Semantic Scholar over `num_cite_rounds=20` to populate `references.bib`, then runs a deterministic regex audit in `compile_latex` that extracts every `\cite{...}` key from `template.tex` and verifies its presence in `references.bib` (plus checks every `\includegraphics` against existing `.png` files and runs `chktex`).
  - **Automated Peer Review (LLM + VLM):**
    - Implemented in [`ai_scientist/perform_llm_review.py`](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/ai_scientist/perform_llm_review.py) and [`ai_scientist/perform_vlm_review.py`](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/ai_scientist/perform_vlm_review.py) — accessed 2026-11-09.
    - `perform_llm_review.py` uses the standard NeurIPS review rubric (`Soundness` 1–4, `Presentation` 1–4, `Contribution` 1–4, `Overall` 1–10, `Confidence` 1–5, `Decision`: Accept/Reject) with multi-reviewer ensembling (`num_reviews_ensemble`), iterative self-reflection (`num_reflections`), and an Area Chair `meta_reviewer_system_prompt`.
    - `perform_vlm_review.py` renders the compiled PDF pages and extracts every figure alongside its caption and main-text references (`figrefs`), asking a VLM (`img_cap_ref_review_prompt` and `img_cap_selection_prompt`) whether the visual plot actually supports the text's claims and selecting which redundant figures to prune to meet page limits.
- **Published Benchmarks & Caveats:**
  - v1 (`arXiv:2408.06292`) reports generating papers for ~$15/paper and achieving 65% accuracy on predicting ICLR 2022 OpenReview decisions. v2 (`arXiv:2504.08066`) submitted 3 generated manuscripts to the ICLR 2025 *I Can't Believe It's Not Better (ICBINB)* workshop under double-blind review; 1 paper scored above the acceptance threshold before voluntary withdrawal. However, the v2 README explicitly caveats: *"The AI Scientist-v2 doesn't necessarily produce better papers than v1, especially when a strong starting template is available... v2 takes a broader, more exploratory approach with lower success rates."*
- **Known Failure Modes & Independent Reproduction Audits (GitHub Issues):**
  1. **Measurable Context & Semantic Drift Across Multi-Hour Runs ([v2 Issue #100](https://github.com/SakanaAI/AI-Scientist-v2/issues/100) — accessed 2026-11-09):** An empirical audit of 6+ hour BFTS runs documented three silent drift modes across stage boundaries:
     - *Ghost lexicon decay*: Specialized domain vocabulary introduced during hypothesis generation decays by Stage 4 and writeup because `overall_summarize()` summarizes execution logs without anchoring to the original ideation lexicon.
     - *Tool-call sequence shift*: Tool invocation patterns drift between stages despite identical stage prompts.
     - *Semantic drift*: Keyword overlap between `idea.json` and the final manuscript drops steadily because `overall_summarize()` only validates that summary JSONs exist (`not None`), never checking semantic alignment with the original hypothesis.
  2. **Schema Blindness in Plot Aggregation — 0 Figures Across 5 Reflection Rounds ([v2 Issue #126](https://github.com/SakanaAI/AI-Scientist-v2/issues/126) — accessed 2026-11-09):** In a multi-run reproduction campaign, `perform_plotting.py` (`aggregate_plots`) gave the LLM file paths to `.npy` experiment outputs (`experiment_data.npy`) without exposing their nested dictionary schemas. Because BFTS nodes generated 37 different top-level key variations, the plotting scripts caught `KeyError` inside `try/except`, exited with status `0` ("ran successfully"), and produced **0 valid figures across all 5 reflection rounds**. Injecting a runtime schema manifest (`keys, types, shapes`) into the prompt before Round 1 immediately produced 8–9 valid publication figures on the first attempt.
  3. **Deferred Summary Persistence Loses 25% of Long Runs ([v2 Issue #127](https://github.com/SakanaAI/AI-Scientist-v2/issues/127) — accessed 2026-11-09):** While BFTS saves `journal.json` incrementally, `overall_summarize()` is only called after all 4 stages finish. In an independent 20-run batch evaluation, **5 of 20 runs** hit wall-clock limits in Stage 3/4 and lost their entire writeup pipeline because `*_summary.json` files were never checkpointed at stage transitions.
  4. **Writeup Retry Loop Deletes Valid PDFs & Ignores LaTeX Errors ([v2 Issue #124](https://github.com/SakanaAI/AI-Scientist-v2/issues/124) — accessed 2026-11-09):** In `perform_icbinb_writeup.py`, if the final page-limit reflection says `"No changes"`, `*_reflection_final_page_limit.pdf` is never written, causing `perform_writeup()` to return `False`; the outer retry loop then executes `rm -f *.pdf` and **deletes all valid PDFs from earlier reflections**. Moreover, `compile_latex()` calls `subprocess.run(["pdflatex", ...])` without `check=True`, silently ignoring broken LaTeX edits in **2 of 8 runs**.
  5. **Pre-Registered Independent Audit (`osf.io/aqchj`, [v2 Issue #133](https://github.com/SakanaAI/AI-Scientist-v2/issues/133) — accessed 2026-11-09):** Across 10 biomedical prompts (24 generated PDFs), an independent audit found that `perform_vlm_review.py` had a hardcoded model whitelist that silently rejected `gemini-2.5-flash`, meaning **0 of 24 papers actually underwent VLM figure verification (`F11`)**, and uncovered an `UnboundLocalError: pdf_path` (`F13`) in the writeup pipeline.
  6. **Catastrophic Process Cleanup & Command Injection ([v2 Issue #122](https://github.com/SakanaAI/AI-Scientist-v2/issues/122), [v2 Issue #123](https://github.com/SakanaAI/AI-Scientist-v2/issues/123), [v1 Issue #251](https://github.com/SakanaAI/AI-Scientist/issues/251) — accessed 2026-11-09):** A single failed worker in `ParallelAgent.step` aborts the entire tree search (#122); end-of-run cleanup sends `SIGTERM` to any process on the host machine whose command line contains `"python"`, `"torch"`, or `"mp"` (#123); and v1 passes unquoted `idea['Name']` to `os.popen(f"chktex {writeup_file}")` (#251).

### 2.4 `stanford-oval/WikiChat` & `HKUDS/Auto-Deep-Research`

#### A. `stanford-oval/WikiChat` (7-Stage Fact-Verification Pipeline)
- **Repository & Papers:** [`stanford-oval/WikiChat`](https://github.com/stanford-oval/WikiChat) — accessed 2026-11-09; Semnani et al., EMNLP 2023 ([`arXiv:2305.14292`](https://arxiv.org/abs/2305.14292) — accessed 2026-11-09) & SPAGHETTI, ACL 2024 ([`arXiv:2406.00592`](https://arxiv.org/abs/2406.00592) — accessed 2026-11-09).
- **Exact 7-Stage Pipeline Mechanism** ([`pipelines/chatbot.py`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/chatbot.py) & [`pipelines/dialogue_state.py`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/dialogue_state.py) — accessed 2026-11-09):
  1. **`query_stage` ([`query.prompt`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/prompts/query.prompt) — accessed 2026-11-09):** Rewrites the conversational turn into self-contained search queries `<search_query>` (or `"None"` if no factual search is needed).
  2. **`search_stage`:** Retrieves passages from a Qdrant vector index using `Snowflake/snowflake-arctic-embed-m-v2.0` or `BAAI/bge-m3` embeddings + a listwise LLM reranker ([`rerank_listwise.prompt`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/prompts/rerank_listwise.prompt) — accessed 2026-11-09).
  3. **`generate_stage` ([`generate_split_claims.prompt`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/prompts/generate_split_claims.prompt) — accessed 2026-11-09):** A standout architectural innovation. Instead of generating a free-text draft and running a second LLM call to split it into claims, WikiChat merges generation and atomic claim decomposition into a single step. The LLM outputs a bulleted list of **self-contained, pronoun-free atomic claims** (annotated with exact dates up to its knowledge cutoff), governed by a strict **parent-claim dependency rule** documented in the prompt source:
     > *"Claims should be split with regards to their parent claim. For example, here the first claim should NOT be 'The Stanford Prison Experiment was conducted in the basement of Encina Hall.' If it is, and if only the first claim passes fact-checking, we will be left with a fact that is too specific to be helpful. Instead: `- The Stanford Prison Experiment was conducted in the basement of Stanford's psychology building.` `- Encina Hall is the name of Stanford's psychology building.`"*
  4. **`llm_claim_search_stage`:** Dispatches an independent retrieval query for **every individual bullet claim** generated in Stage 3 to verify parametric claims against the corpus.
  5. **`all_single_search_results` + `filter_information_stage` ([`filter_irrelevant_info.prompt`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/prompts/filter_irrelevant_info.prompt) — accessed 2026-11-09):** Merges passages from Stage 2 (user query search) and Stage 4 (per-claim verification search), deduplicates near-identical passages using token-level **Jaccard similarity (`jaccard_similarity > 0.8`)** in `dialogue_state.py`, and runs a batch LLM filter to extract only verified `<relevant_content>` bullets (dropping passages that return `"None"`).
  6. **`draft_stage` ([`draft_w_citation.prompt`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/prompts/draft_w_citation.prompt) — accessed 2026-11-09):** Synthesizes the response exclusively from the top 10 verified `<documents>` (`filtered_search_results[:10]`) with `[1]` inline citations and strict temporal tense checking against `{{ today }}`.
  7. **`refine_stage` ([`refine_w_feedback.prompt`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/prompts/refine_w_feedback.prompt) — accessed 2026-11-09):** Self-critiques the draft on 4 numeric rubrics (`Relevant`, `Correct Time`, `Natural`, `Non-Repetitive`, each 0–100) over the last `num_turns=2` turns (chosen specifically because a 1-turn window failed to catch repetitions from 2 turns prior) and emits `<revised_response>` while preserving `[n]` citations.
- **Published Benchmarks:** WikiChat reports **97.3% factual accuracy** on human-evaluated open-domain conversations (EMNLP 2023) and **+5.9% factual accuracy** over multilingual baselines in SPAGHETTI (ACL 2024).

#### B. `HKUDS/Auto-Deep-Research` (AutoAgent)
- **Repository & Paper:** [`HKUDS/Auto-Deep-Research`](https://github.com/HKUDS/Auto-Deep-Research) — accessed 2026-11-09; Tang et al., *AutoAgent: A Fully-Automated and Zero-Code Framework for LLM Agents* ([`arXiv:2502.05957`](https://arxiv.org/abs/2502.05957) — accessed 2026-11-09).
- **Exact Mechanism:**
  - Implemented in [`autoagent/core.py`](https://github.com/HKUDS/Auto-Deep-Research/blob/main/autoagent/core.py) and [`autoagent/agents/system_agent/`](https://github.com/HKUDS/Auto-Deep-Research/tree/main/autoagent/agents/system_agent) — accessed 2026-11-09.
  - Uses a `MetaChain` swarm-style handoff loop where a `System Triage Agent` delegates tasks via `transfer_to_*` tools to three specialized workers: `Web Surfer Agent` (`MarkdownBrowser`), `File Surfer Agent` (converts PDFs/DOCX/PPTX/audio to Markdown via `mdconvert` and navigates viewport chunks via `page_up_markdown`, `page_down_markdown`, `find_on_page_ctrl_f`), and `Coding Agent` (executes Python/bash in a Docker container).
  - Includes an XML-based tool-call shim (`fn_call_converter.py`) for models lacking native function-calling APIs, and a ChromaDB `TextMemory` (`paper_memory.py`, 4096-token chunks).
- **Known Failure Modes & Contrast with WikiChat:**
  - Unlike WikiChat or PaperQA2, `Auto-Deep-Research` has **no atomic claim verification, no source relevance scoring, and no periodic context compression**—`MetaChain.run` simply appends sub-agent message histories into a growing list until `case_resolved` or `case_not_resolved` is called.
  - In practice, users hit frequent `KeyError: 'tool_calls'` crashes when using DeepSeek/OpenRouter models ([Issues #19](https://github.com/HKUDS/Auto-Deep-Research/issues/19), [#25](https://github.com/HKUDS/Auto-Deep-Research/issues/25), [#28](https://github.com/HKUDS/Auto-Deep-Research/issues/28) — accessed 2026-11-09), Docker container hang/pull failures ([Issues #17](https://github.com/HKUDS/Auto-Deep-Research/issues/17), [#30](https://github.com/HKUDS/Auto-Deep-Research/issues/30) — accessed 2026-11-09), and Playwright DOM detachment crashes in `_get_page_markdown()` ([Issue #27](https://github.com/HKUDS/Auto-Deep-Research/issues/27) — accessed 2026-11-09).

## 3. Type D: Benchmark-Driven Deep Research Agents — Deep Inspection

### 3.1 `Alibaba-NLP/DeepResearch` (Tongyi DeepResearch + WebResearcher / WebResummer / AgentFold / ParallelMuse)

- **Repository & Papers:** [`Alibaba-NLP/DeepResearch`](https://github.com/Alibaba-NLP/DeepResearch) — accessed 2026-11-09; Tongyi DeepResearch Technical Report ([`arXiv:2510.24701`](https://arxiv.org/abs/2510.24701) — accessed 2026-11-09); WebResearcher / IterResearch (Qiao et al., [`arXiv:2509.13309`](https://arxiv.org/abs/2509.13309) — accessed 2026-11-09); ReSum (Wu et al., [`arXiv:2509.13313`](https://arxiv.org/abs/2509.13313) — accessed 2026-11-09).
- **Model Architecture:** `Tongyi-DeepResearch-30B-A3B` (Mixture-of-Experts with 30.5B total parameters and only **3.3B active parameters per token**, 128K context length).
- **Exact Mechanisms for Context Management & Preventing Context Rot:**
  The repository contains both a standard ReAct baseline and four specialized context-folding architectures under `WebAgent/`:
  1. **Goal-Conditioned Sub-Model Visit Extraction (`inference/tool_visit.py` & `inference/prompt.py`):**
     - Even in standard ReAct mode ([`inference/react_agent.py`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/inference/react_agent.py) — accessed 2026-11-09, `MAX_LLM_CALL_PER_RUN = 100`), when the agent calls `visit(url, goal)`, raw webpage Markdown from Jina Reader is **never** appended to the main agent's context.
     - Instead, [`tool_visit.py`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/inference/tool_visit.py) — accessed 2026-11-09 truncates the raw page to 95,000 tokens and invokes an external LLM call (`SUMMARY_MODEL_NAME`) with `EXTRACTOR_PROMPT` ([`inference/prompt.py`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/inference/prompt.py) — accessed 2026-11-09) conditioned on the agent's explicit `goal`, returning structured JSON: `{"rational": "...", "evidence": "...most relevant original context...", "summary": "..."}`.
  2. **Markovian Workspace Reconstruction — `IterResearch` / `WebResearcher` ([`WebAgent/WebResearcher/README.md`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/WebAgent/WebResearcher/README.md) — accessed 2026-11-09):**
     - Explicitly diagnoses three failure modes of append-only mono-contextual ReAct: **(1) Cognitive Workspace Suffocation**, **(2) Irreversible Noise Contamination**, and **(3) Lack of Periodic Synthesis**.
     - Reformulates long-horizon research as a **Markov Decision Process (MDP)** over discrete rounds $\mathcal{S}_t$. In each round $t$, the agent sees only the original question, the compressed `Report_{t-1}` from the previous round, and the most recent tool observation `Action_{t-1}` + `Tool_Response_{t-1}`. It then outputs three structured blocks:
       - `Think`: Scratchpad reasoning for the current step — **discarded immediately after round $t$** so internal monologue never clutters future rounds.
       - `Report`: Updated central evolving memory that integrates new verified facts from `Tool_Response_{t-1}` into `Report_{t-1}` — **carried forward to round $t+1$**.
       - `Action`: Next tool call or final answer.
  3. **Periodic Context Summarization — `ReSum` ([`WebAgent/WebResummer/src/react_agent.py`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/WebAgent/WebResummer/src/react_agent.py) & [`prompt.py`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/WebAgent/WebResummer/src/prompt.py) — accessed 2026-11-09):**
     - Runs standard ReAct until token count approaches a threshold, then invokes `ReSumTool-30B` (`QUERY_SUMMARY_PROMPT`) to compress the trajectory into `<summary>...</summary>` (listing confirmed facts, failed queries, and open gaps while strictly forbidding unverified speculation) and resets the conversation history to `[system_prompt, user_question, <summary>]`.
  4. **In-Step Context Folding — `AgentFold` ([`WebAgent/AgentFold/infer.py`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/WebAgent/AgentFold/infer.py) — accessed 2026-11-09):**
     - At every step, the model itself generates four XML blocks: `<think>`, `<compress>` (dynamically folding previous step history), `<motivation>`, and `<action>`.
  5. **Heavy Mode / Parallel Trajectory Aggregation — `ParallelMuse` ([`WebAgent/ParallelMuse/compressed_reasoning_aggregation.py`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/WebAgent/ParallelMuse/compressed_reasoning_aggregation.py) — accessed 2026-11-09):**
     - Runs $K$ parallel trajectories; instead of naive majority voting or feeding raw trajectories that overflow context, it first distills each trajectory via `REPORT_PROMPT` into three sections (`1. Solution Planning`, `2. Solution Methods` with essential tool fragments only, `3. Final Reasoning`), then feeds the $K$ compressed reports into `INTEGRATE_PROMPT` to select the best-verified conclusion.
- **Published Benchmarks vs. Independent Verification & Known Failure Modes:**
  - **Published Scores ([`README.md`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/README.md) — accessed 2026-11-09):** Reports 32.9% on HLE (Heavy Mode), 43.4% on BrowseComp-EN, 46.7% on BrowseComp-ZH, 70.9% on GAIA, and 75.0% on xbench-DeepSearch.
  - **Failure Mode 1 — Missing Heavy/Context-Management Code in Main Inference Script ([Issue #229](https://github.com/Alibaba-NLP/DeepResearch/issues/229) — accessed 2026-11-09):** Users inspecting `inference/react_agent.py` noted that the main Tongyi DeepResearch inference script only implements the flat append-only ReAct loop (`messages.append`), leaving users confused as to where the paper's Markovian context folding resides (it was only released later under separate subprojects in `WebAgent/`).
  - **Failure Mode 2 — Search-Time Benchmark Data Contamination ([Issue #251](https://github.com/Alibaba-NLP/DeepResearch/issues/251) — accessed 2026-11-09):** A critical audit reported in Issue #251 (citing `arXiv:2508.13180`) demonstrates that because `tool_search.py` does not block `huggingface.co`, `github.com`, or benchmark mirrors, Deep Research agents searching verbatim HLE/benchmark prompts locate unencrypted JSON/CSV ground-truth files on the live web and extract answers directly (~3% of HLE questions).
  - **Failure Mode 3 — Severe Search-Engine & Judge Sensitivity in Independent Reproductions ([Issue #218](https://github.com/Alibaba-NLP/DeepResearch/issues/218) & [Issue #223](https://github.com/Alibaba-NLP/DeepResearch/issues/223) — accessed 2026-11-09):** Independent evaluators running `Tongyi-DeepResearch-30B-A3B` with the official prompt achieved only **~20% on BrowseComp-EN** when substituting Bing for Serper (#218, vs. 43.4% reported) and **62–68% on xbench-DeepSearch** (vs. 75.0% reported, #223) due to search backend variance and automated judge strictness on equivalent phrasing.

### 3.2 `MiroMindAI/MiroThinker` (MiroThinker v1.0 / v1.5 / v1.7 & MiroFlow)

- **Repository & Paper:** [`MiroMindAI/MiroThinker`](https://github.com/MiroMindAI/MiroThinker) — accessed 2026-11-09; Team MiroMind, *MiroThinker: Pushing the Performance Boundaries of Open-Source Research Agents via Model, Context, and Interactive Scaling* ([`arXiv:2511.11793`](https://arxiv.org/abs/2511.11793) — accessed 2026-11-09).
- **Exact Mechanism for Interactive Scaling & Context Window Management (`keep_tool_result: 5`):**
  - Configured in [`apps/miroflow-agent/conf/agent/mirothinker_1.7_keep5_max300.yaml`](https://github.com/MiroMindAI/MiroThinker/blob/main/apps/miroflow-agent/conf/agent/mirothinker_1.7_keep5_max300.yaml) and implemented in [`apps/miroflow-agent/src/llm/base_client.py`](https://github.com/MiroMindAI/MiroThinker/blob/main/apps/miroflow-agent/src/llm/base_client.py) (`_remove_tool_result_from_messages`, lines 124–195) and [`apps/miroflow-agent/src/core/orchestrator.py`](https://github.com/MiroMindAI/MiroThinker/blob/main/apps/miroflow-agent/src/core/orchestrator.py) — accessed 2026-11-09.
  - **Recency-Masked Tool Output Retention (`keep_tool_result = 5`):** To survive 300–600 tool calls without overflowing the 256K context window or suffering attention dilution from stale search snippets, `_remove_tool_result_from_messages` retains:
    1. The initial `user` task prompt (`user_indices[0]`),
    2. **All** `assistant` turns across the entire trajectory (preserving every `<think>` block and `<tool_call>` invocation so the agent knows what it already searched and deduced), and
    3. **Only the last `k = 5` `user`/`tool` observation messages** (`tool_result_indices[-5:]`), stripping out all older raw tool payloads!
  - Because the model is explicitly RL-trained with this sliding 5-observation window, it learns to copy any vital facts from a tool output into its next `<think>` turn before that tool output ages out of the 5-turn window ([Issue #116](https://github.com/MiroMindAI/MiroThinker/issues/116) — accessed 2026-11-09).
  - **Duplicate Query Tracking & Rollback:** `orchestrator.py` tracks `self.used_queries` to block repeated identical search calls and enforces `MAX_CONSECUTIVE_ROLLBACKS` (`context_compress_limit: 5`).
- **Empirical Turn-Cap Finding (300 vs. 400 Turns):**
  - In **[Issue #137](https://github.com/MiroMindAI/MiroThinker/issues/137) — accessed 2026-11-09**, contributors profiled full benchmark runs across **BrowseComp-EN** (1,266 tasks, avg 43 min/task) and **BrowseComp-ZH** (289 tasks, avg 48.6 min/task, max 265 min/task) and found empirically that **tasks not solved within 300 turns have ~0% probability of succeeding between turns 300 and 400**. Lowering `max_turns` from 400 to 300 (`mirothinker_1.7_keep5_max300.yaml`) cut tail latency by 25% with zero accuracy loss.
- **Published Benchmarks ([`README.md`](https://github.com/MiroMindAI/MiroThinker/blob/main/README.md) — accessed 2026-11-09):**
  - `MiroThinker-1.7` (235B-A22B): **74.0%** on BrowseComp, **75.3%** on BrowseComp-ZH, **82.7%** on GAIA-Val-165, **42.9%** on HLE-Text, **81.9%** on DeepSearchQA.
  - `MiroThinker-1.7-mini` (30B-A3B): **64.2%** on BrowseComp, **67.9%** on BrowseComp-ZH, **80.7%** on GAIA-Val-165, **34.9%** on HLE-Text.
- **Known Failure Modes & GitHub Issues:**
  1. **Severe MCP Process-Spawning & Concurrency Bottlenecks ([Issue #137](https://github.com/MiroMindAI/MiroThinker/issues/137) & [PR #139](https://github.com/MiroMindAI/MiroThinker/pull/139) — accessed 2026-11-09):** In `libs/miroflow-tools/src/miroflow_tools/manager.py`, every single tool call opened a brand-new `stdio_client` MCP subprocess, performed the handshake, executed one call, and killed the process—multiplying by 300 turns to waste 2–5 minutes of pure subprocess overhead per task. Under `MAX_CONCURRENT=60`, sequential MCP init averaged **234s (max 945s)** and E2B sandbox creation spiked from **33s to 631s**.
  2. **Benchmark-Hardcoded Short Answers & Refusal to Summarize at `max_turns` ([Issue #158](https://github.com/MiroMindAI/MiroThinker/issues/158) — accessed 2026-11-09):** Users attempting to generate long-form research reports discovered that `generate_agent_summarize_prompt` in `apps/miroflow-agent/src/utils/prompt_utils.py` hardcodes: *"Your final answer should be a number, OR as few words as possible... wrap it in `\boxed{}`"*. Furthermore, maintainers confirmed in Issue #158 that the long-form report prompt used on `dr.miromind.ai` is **closed-source**, and when the open-source model hits `max_turns`, it frequently ignores the final synthesis prompt and emits another `<use_mcp_tool>` tag instead of answering.

### 3.3 `RUC-NLPIR/WebThinker` (Deep Web Explorer + Autonomous Think-Search-and-Draft)

- **Repository & Paper:** [`RUC-NLPIR/WebThinker`](https://github.com/RUC-NLPIR/WebThinker) — accessed 2026-11-09; Li et al., *WebThinker: Empowering Large Reasoning Models with Deep Research Capability* (NeurIPS 2025, [`arXiv:2504.21776`](https://arxiv.org/abs/2504.21776) — accessed 2026-11-09).
- **Exact Mechanisms:**
  - **In-Thinking Special-Token Interception** ([`scripts/run_web_thinker.py`](https://github.com/RUC-NLPIR/WebThinker/blob/main/scripts/run_web_thinker.py) & [`scripts/run_web_thinker_report.py`](https://github.com/RUC-NLPIR/WebThinker/blob/main/scripts/run_web_thinker_report.py) — accessed 2026-11-09):
    - Instead of breaking reasoning into multi-turn chat messages, WebThinker streams a single continuous `<think>` generation (`max_tokens=81920`) from a Large Reasoning Model (`QwQ-32B` or `WebThinker-R1-32B`) with stop strings set to `</wid_search_query|>`, `<|end_write_section|>`, `<|begin_check_article|>`, and `<|end_edit_article|>`. When a stop token triggers, the harness executes the tool, appends the result tag directly into the ongoing `<think>` stream, and resumes generation from the exact token offset.
  - **Subagent Context Shielding — `Deep Web Explorer` ([`scripts/prompts/prompts.py`](https://github.com/RUC-NLPIR/WebThinker/blob/main/scripts/prompts/prompts.py) — accessed 2026-11-09):**
    - When the primary LRM emits `<|begin_search_query|>...<|end_search_query|>`, the primary model's context window is **completely shielded** from raw search snippets and HTML pages.
    - An auxiliary model (`Qwen2.5-32B-Instruct`) first extracts the current `search_intent` from the last 4,000 characters of reasoning (`get_search_intent_instruction`), then runs an inner autonomous browsing loop (`get_deep_web_explorer_instruction`, up to 10 sub-turns) where the auxiliary model can issue follow-up `<|begin_search_query|>` or `<|begin_click_link|>` actions (`extract_relevant_info` via Jina/Crawl4AI), and finally returns only a distilled `**Final Information**` block into the primary LRM's `<|begin_search_result|>` tag.
  - **External Memory Report Drafting (`Autonomous Think-Search-and-Draft`, [`scripts/prompts/prompts_report.py`](https://github.com/RUC-NLPIR/WebThinker/blob/main/scripts/prompts/prompts_report.py) — accessed 2026-11-09):**
    - Before starting, an auxiliary call generates a numbered research plan (`get_search_plan_instruction`, $\le 8$ steps).
    - While thinking and searching, the primary LRM writes the report incrementally into an **external `article` string buffer** (outside its own context window) using three special tools delegated to the auxiliary model:
      1. `<|begin_write_section|>section_name\noutline_and_notes<|end_write_section|>`: The harness runs BM25 retrieval (`rank_bm25`) over `seq['gathered_info']` (all web pages visited so far) to fetch the top 10 relevant documents (`max_words=4000`), and the auxiliary model writes the full section (`get_write_section_instruction`).
      2. `<|begin_check_article|>`: Returns **only the current section headings/outline** of the external draft (`extract_markdown_outline`) into `<|begin_check_article_result|>`, allowing the LRM to check structural progress without re-reading thousands of drafted words!
      3. `<|begin_edit_article|>edit_instruction<|end_edit_article|>`: Auxiliary model applies targeted edits to the external draft (`get_edit_article_instruction`).
- **Published Benchmarks ([`README.md`](https://github.com/RUC-NLPIR/WebThinker/blob/main/README.md) — accessed 2026-11-09):**
  - `WebThinker-QwQ-32B` (RL-trained via iterative online DPO): **60.8%** on GAIA-Text-103, **57.3%** on WebWalkerQA, **25.0%** on HLE-Text-500, and **8.0 / 8.1 / 8.3** (Comprehensiveness / Completeness / Readability) on Glaive scientific report evaluation.
- **Known Failure Modes & GitHub Issues:**
  1. **Plaintext Benchmark Test Sets Committed Inside the Repository ([Issue #32](https://github.com/RUC-NLPIR/WebThinker/issues/32) — accessed 2026-11-09):** The repository commits unencrypted benchmark files directly at `data/GAIA/dev.json`, `data/GPQA/diamond.json`, `data/HLE/test.json`, and `data/WebWalkerQA/test.json` ([`RUC-NLPIR/WebThinker/tree/main/data`](https://github.com/RUC-NLPIR/WebThinker/tree/main/data) — accessed 2026-11-09), creating direct web-search leakage for any agent searching GitHub.
  2. **Zero Citation Enforcement in Report Planning:** In [`scripts/prompts/prompts_report.py`](https://github.com/RUC-NLPIR/WebThinker/blob/main/scripts/prompts/prompts_report.py) — accessed 2026-11-09 (`get_search_plan_instruction`), the prompt explicitly instructs: *"No need to mention citations or references. Focus on the structure and content of the report."* Because the Glaive benchmark LLM judge ([`evaluate_report.py`](https://github.com/RUC-NLPIR/WebThinker/blob/main/scripts/evaluate/evaluate_report.py) — accessed 2026-11-09) grades only Comprehensiveness, Completeness, Readability, and Consistency without checking source URLs, the system optimizes for prose fluency over verifiable citations.
  3. **Silent `WebExplorer` Termination on Stop-Token Mismatch ([Issue #31](https://github.com/RUC-NLPIR/WebThinker/issues/31) — accessed 2026-11-09):** Because tool interception relies on exact string suffixes (`response.rstrip().endswith(END_SEARCH_QUERY)`), serving models via vLLM/GGUF that strip special tokens or append trailing whitespace causes the `while not seq['finished']:` loop to exit after 1 turn without ever invoking `WebExplorer`.
  4. **Bing Search API Retirement Breaks Reproducibility ([Issue #35](https://github.com/RUC-NLPIR/WebThinker/issues/35) — accessed 2026-11-09):** All paper results used Microsoft's Bing Search API, which was retired on August 11, 2025.

### 3.4 `TIGER-AI-Lab/OpenResearcher`

- **Repository & Paper:** [`TIGER-AI-Lab/OpenResearcher`](https://github.com/TIGER-AI-Lab/OpenResearcher) — accessed 2026-11-09; Li et al., *OpenResearcher: A Fully Open Pipeline for Long-Horizon Deep Research Trajectory Synthesis* ([`arXiv:2603.20278`](https://arxiv.org/abs/2603.20278) — accessed 2026-11-09).
- **Exact Mechanism for Offline Trajectory Synthesis & Viewport Browsing:**
  - Implemented in [`deploy_agent.py`](https://github.com/TIGER-AI-Lab/OpenResearcher/blob/main/deploy_agent.py), [`browser.py`](https://github.com/TIGER-AI-Lab/OpenResearcher/blob/main/browser.py), and [`data_utils.py`](https://github.com/TIGER-AI-Lab/OpenResearcher/blob/main/data_utils.py) — accessed 2026-11-09.
  - **Offline Corpus (`OpenResearcher-Corpus`, ~15M documents / 11B tokens):** Solves the prohibitive API cost and non-reproducibility of live web search by indexing FineWeb + Wikipedia +BrowseComp-Plus gold documents with Tevatron (`Qwen3-Embedding-8B` dense FAISS or BM25) behind a local HTTP service (`LocalServiceBrowserBackend`).
  - **Stateful Line-Numbered Viewport Tools (`SimpleBrowserTool`):** Instead of dumping full pages or relying on a secondary LLM summarizer, `browser.py` implements OpenAI's `openai_harmony` / `gpt_oss` stateful browser protocol with three tools:
    1. `browser.search(query, topn=10)`: Returns titles, URLs, and snippets assigned to a monotonically increasing page `[cursor]`.
    2. `browser.open(id, cursor, loc, num_lines)`: Opens a link ID `【{id}†.*】` or URL and renders a specific **line-numbered viewport slice** (`L{line_start}-L{line_end}`) so the model scrolls (`loc`, `num_lines`) without flooding context.
    3. `browser.find(pattern, cursor)`: Executes in-page regex/substring search on the cached page at `cursor` and jumps the viewport to matching line numbers.
  - **Cursor-and-Line Citation Constraint (`data_utils.py`):** `DEVELOPER_CONTENT` enforces exact line-range citations tied to browser state:
    > *"The `cursor` appears in brackets before each browsing display: `[{cursor}]`. Cite information from the tool using the following format: `【{cursor}†L{line_start}(-L{line_end})?】`, for example: `【6†L9-L11】` or `【8†L3】`. Do not quote more than 10 words directly from the tool output."*
  - Distills 96K trajectories (up to 100+ turns per trajectory) synthesized by `GPT-OSS-120B` into `Qwen3-30B-A3B-Thinking` via SFT (`OpenResearcher-30B-A3B`).
- **Published Benchmarks vs. Independent Verification & Known Failure Modes:**
  - **Published Scores ([`README.md`](https://github.com/TIGER-AI-Lab/OpenResearcher/blob/main/README.md) — accessed 2026-11-09):** Reports **54.8%** on BrowseComp-Plus, **32.5%** on BrowseComp, **72.8%** on GAIA-Text, **29.0%** on HLE, and **63.0%** on xbench-DeepResearch.
  - **Failure Mode 1 — Benchmark Scaffold Discrepancy in Table 1 ([Issue #3](https://github.com/TIGER-AI-Lab/OpenResearcher/issues/3) & [Issue #4](https://github.com/TIGER-AI-Lab/OpenResearcher/issues/4) — accessed 2026-11-09):** Independent researchers pointed out that Table 1 lists Tongyi DeepResearch at **44.5%** on BrowseComp-Plus (taken from the Tevatron leaderboard using a generic `Qwen3-Embedding-8B` scaffold), whereas running Tongyi DeepResearch with its own native scaffold on BrowseComp-Plus achieves **~68%**. This highlights how evaluating a model outside its trained tool/context scaffold depresses scores by >20 percentage points.
  - **Failure Mode 2 — Severe SFT Overfitting to Benchmark Question Templates ([Issue #1](https://github.com/TIGER-AI-Lab/OpenResearcher/issues/1) — accessed 2026-11-09):** When a user sent a simple `"Hi"` to `OpenResearcher-30B-A3B` without the Harmony browser scaffold, the model immediately hallucinated a random benchmark question inside `<think>`: *`We need to answer: "What is the name of the 2024 novel by E. L. James that features a protagonist named Kate?"`* and emitted `<tool_call>`, proving that heavy trajectory SFT without general conversational regularization causes catastrophic template lock-in.
  - **Failure Mode 3 — Multi-Second Retrieval Latency on CPU FAISS ([Issue #6](https://github.com/TIGER-AI-Lab/OpenResearcher/issues/6) & [Issue #8](https://github.com/TIGER-AI-Lab/OpenResearcher/issues/8) — accessed 2026-11-09):** `backend.py` defaults to brute-force `FaissFlatSearcher` over 15M documents (~15GB GPU VRAM required for dense search), causing multi-second per-query latency unless users move FAISS to GPU or use the newly released subset [`OpenResearcher-Corpus-Gold-Doc`](https://huggingface.co/datasets/OpenResearcher/OpenResearcher-Corpus-Gold-Doc) — accessed 2026-11-09.

## 4. Cross-Cutting Synthesis: How Type C & Type D Prevent Context Rot and Synthesis Drift

Long-horizon research agents fail primarily when raw retrieval outputs accumulate in an append-only message list—causing **attention dilution ("context rot")**, **irreversible noise contamination**, and **synthesis drift** (where the final writeup loses domain precision or drops verified citations). Across the 10 inspected repositories, six distinct architectural patterns emerge:

| Mechanism | Representative Repo(s) | Exact Implementation | What It Solves | What Still Breaks |
|---|---|---|---|---|
| **1. Recency-Masked Tool Results (`keep_tool_result: k`)** | `MiroMindAI/MiroThinker` (`base_client.py`) | Retains initial user prompt + **all** assistant `<think>` & `<tool_call>` turns, but strips raw `<tool_response>` payloads older than the last $k=5$ turns (`keep_tool_result: 5`). | Prevents 256K OOM across 300 turns with **zero extra LLM summarization cost**. Forces agent to copy key facts into `<think>`. | If the agent fails to transcribe a URL or exact number into its `<think>` turn within 5 steps, that raw evidence is permanently lost from context. |
| **2. Markovian Workspace Reconstruction (`Think`/`Report`/`Action`)** | `Alibaba-NLP/DeepResearch` (`WebResearcher`, `ReSum`, `AgentFold`) | Each round outputs `Think` (discarded after round), `Report` (evolving factual summary carried forward), and `Action`. Context at step $t$ is strictly `[Question, Report_{t-1}, Tool_Obs_{t-1}]`. | Eliminates cognitive workspace suffocation and dead-end search noise completely; $O(1)$ context growth per turn. | **Summary lossiness:** If `Report_t` compresses away a nuanced caveat or citation URL, later steps cannot recover it without re-searching. |
| **3. Goal-Conditioned Visit / Subagent Shielding** | `Alibaba-NLP/DeepResearch` (`tool_visit.py`), `RUC-NLPIR/WebThinker` (`Deep Web Explorer`) | Primary reasoning model never sees raw HTML/Markdown. A sub-model (`EXTRACTOR_PROMPT` or `WebExplorer`) reads up to 95K tokens conditioned on `goal` / `search_intent` and returns only `{rational, evidence, summary}`. | Keeps primary reasoning trajectory clean and high-signal; enables deep multi-click navigation inside a single logical step. | Doubles LLM call count per page visit; sub-model may hallucinate or over-prune if `goal` is poorly specified. |
| **4. Ranking & Contextual Summarization (`RCS` 0–10)** | `Future-House/paper-qa` (`core.py`, `docs.py`) | Maps `summary_llm` concurrently over top `evidence_k` (10–30) hybrid-retrieved chunks to produce JSON `{summary, relevance_score: 0..10}` with `pqac-hash` keys + journal/retraction metadata; prunes `<=1` and keeps top `answer_max_sources` (5–15). | Explicitly grades evidence quality before synthesis; preserves exact numbers/quotes; prevents low-relevance chunks from polluting the answer generator. | High token cost (20–30 parallel LLM calls per `GatherEvidence` step); raw chunk text is discarded after RCS ([Issue #1253](https://github.com/Future-House/paper-qa/issues/1253) — accessed 2026-11-09). |
| **5. External Draft Memory + Outline-Only Audit** | `RUC-NLPIR/WebThinker` (`prompts_report.py`), `stanford-oval/storm` (`ConvToSection`) | Draft sections are written in parallel (STORM) or stored in an external buffer outside the reasoning context (`WebThinker` `<|begin_write_section|>`), while `<|begin_check_article|>` returns only the Markdown heading outline. | Prevents the growing 5,000-word report draft itself from consuming the agent's reasoning window; eliminates section-to-section repetition. | Weak cross-section coherence unless a final polish pass (`PolishPage`) or global claim table reconciles terminology. |
| **6. Stateful Viewport & Line-Range Cursors (`[cursor]`, `loc`, `num_lines`)** | `TIGER-AI-Lab/OpenResearcher` (`browser.py`), `HKUDS/Auto-Deep-Research` (`FileSurfer`) | Pages are cached locally by `cursor` ID; agent reads 50-line slices (`browser.open(cursor, loc, num_lines)`) or jumps to regex matches (`browser.find(pattern, cursor)`), citing `【6†L9-L11】`. | Zero summarization latency/cost; preserves 100% verbatim source text and exact line provenance. | Increases turn count (requires 3–5 scroll/find turns per document instead of 1 summarized visit). |

> [!WARNING]
> **Critical Lesson from `AI-Scientist-v2` ([Issue #100](https://github.com/SakanaAI/AI-Scientist-v2/issues/100) — accessed 2026-11-09):** Stage-boundary summarization (`overall_summarize`) **causes measurable semantic and lexical drift ("ghost lexicon decay")** when the summarizer compresses stage logs without re-anchoring to the initial hypothesis/query lexicon and without persisting an immutable structured evidence table alongside the prose summary.

## 5. Benchmark Integrity & Independent Verification Audit

A central finding of our GitHub Issues investigation is that **published benchmark numbers across both Type C and Type D suffer from severe evaluation bugs, search-time data contamination, and scaffold lock-in**:

1. **Search-Time Data Contamination on Live Web Benchmarks ([`Alibaba-NLP/DeepResearch` Issue #251](https://github.com/Alibaba-NLP/DeepResearch/issues/251) & [`RUC-NLPIR/WebThinker` Issue #32](https://github.com/RUC-NLPIR/WebThinker/issues/32) — accessed 2026-11-09):**
   - `WebThinker` literally commits plaintext JSON test sets for `GAIA`, `GPQA-Diamond`, `HLE`, and `WebWalkerQA` in its public GitHub repository (`data/`).
   - Because standard `tool_search.py` implementations do not blacklist `github.com`, `huggingface.co`, or dataset mirrors, agents evaluated with live Google/Serper search can retrieve ground-truth benchmark files directly during evaluation (~3% confirmed rate on HLE per `arXiv:2508.13180`).
2. **Vacuous `1.0` Recall Metric Bug ([`stanford-oval/storm` Issue #572](https://github.com/stanford-oval/storm/issues/572) — accessed 2026-11-09):**
   - STORM's NAACL 2024 evaluation script (`eval/metrics.py`) returns `1.0` whenever a ground-truth section heading contains zero named entities (`if len(g) == 0: return 1`), artificially inflating published entity recall scores on common headings like `"Overview"` or `"History"`.
3. **Scaffold & Search-Engine Sensitivity of 20+ Percentage Points ([`OpenResearcher` Issue #3](https://github.com/TIGER-AI-Lab/OpenResearcher/issues/3), [`Alibaba` Issue #218](https://github.com/Alibaba-NLP/DeepResearch/issues/218), [`Alibaba` Issue #223](https://github.com/Alibaba-NLP/DeepResearch/issues/223) — accessed 2026-11-09):**
   - `Tongyi-DeepResearch-30B-A3B` drops from **~68% to 44.46%** on BrowseComp-Plus when evaluated under the generic Tevatron scaffold rather than its native prompt/tool loop (`OpenResearcher` Issue #3), and drops from **43.4% to ~20%** on BrowseComp-EN when switching from Serper (Google) to Bing (`Alibaba` Issue #218).
4. **Silent Bypass of Automated Verification Gates ([`AI-Scientist-v2` Issue #133](https://github.com/SakanaAI/AI-Scientist-v2/issues/133) — accessed 2026-11-09):**
   - A pre-registered audit (`osf.io/aqchj`) found that hardcoded model-name checks silently skipped VLM figure verification in **24 of 24 runs**, demonstrating that verification stages must fail loudly rather than silently bypassing checks.

## 6. Specific Mechanisms to Borrow for Our Research Pipeline (`CLAUDE.md`)

To upgrade our `CLAUDE.md` R3 research workflow and Tier 3 multi-agent benchmark methodology while avoiding both our current limitations and the failure modes uncovered above, we should adopt **seven concrete mechanisms**:

### 6.1 Borrow from `stanford-oval/WikiChat`: Merged Atomic Claim Generation + Parent-Claim Decomposition
- **Source:** [`pipelines/prompts/generate_split_claims.prompt`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/prompts/generate_split_claims.prompt) & [`pipelines/dialogue_state.py`](https://github.com/stanford-oval/WikiChat/blob/main/pipelines/dialogue_state.py) — accessed 2026-11-09.
- **How It Improves Our System:** Our `CLAUDE.md` R3 "Verify & Strip" step currently verifies claims *after* drafting prose, where compound sentences make partial verification messy. By adopting WikiChat's **parent-claim splitting rule** (decomposing specific claims into a general parent claim + a specific child claim, pronoun-free, with explicit dates) and running **token-level Jaccard deduplication (`> 0.8`)** on retrieved passages before synthesis, we ensure that if a hyper-specific sub-claim fails verification, the verified parent claim survives cleanly without leaving orphaned fragments.

### 6.2 Borrow from `Future-House/paper-qa`: Ranking & Contextual Summarization (RCS 0–10) with Provenance Metadata & Hash Keys
- **Source:** [`src/paperqa/core.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/core.py), [`src/paperqa/prompts.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/prompts.py), and [`src/paperqa/clients/retractions.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/clients/retractions.py) — accessed 2026-11-09.
- **How It Improves Our System:**
  1. **Pre-Synthesis RCS Gate:** Score every retrieved excerpt `0–10` via a fast sub-model that extracts exact numbers, quotes, and equations into `{summary, relevance_score}`, discarding chunks `<= 2` before synthesis.
  2. **Pre-Existing Citation Stripping (`strip_citations`):** Strip secondary inline citations (`[1]`, `(Author, Year)`) from raw fetched text before passing excerpts to the writer, preventing the writer from confusing a source's internal bibliography with our own verified sources.
  3. **What We Avoid from PaperQA2:** Unlike PaperQA2 ([Issue #1253](https://github.com/Future-House/paper-qa/issues/1253) — accessed 2026-11-09), we will retain a pointer (`cursor` + line range from `OpenResearcher`) to the raw passage on disk so the synthesis agent can inspect verbatim text whenever an RCS summary is ambiguous, and we will store indices in JSONL/Parquet/DuckDB rather than `pickle` ([Issue #1325](https://github.com/Future-House/paper-qa/issues/1325) — accessed 2026-11-09).

### 6.3 Borrow from `stanford-oval/storm`: Structural TOC-Grounded Persona Discovery + Co-STORM Intent Tree
- **Source:** [`persona_generator.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/storm_wiki/modules/persona_generator.py) & [`information_insertion_module.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/collaborative_storm/modules/information_insertion_module.py) — accessed 2026-11-09.
- **How It Improves Our System:** In our `CLAUDE.md` "Explore" phase, instead of zero-shot subtopic decomposition, first fetch the Tables of Contents (H2–H4 headings) of 3–5 canonical reference articles/repos in the target domain and generate adversarial/orthogonal reviewer personas from those structural outlines. Store findings in a hierarchical Markdown/JSON intent tree (`KnowledgeNode`) rather than a flat scratchpad.
- **What We Avoid from STORM:** Fix the multi-citation regex truncation bug (`r"([.!?])\s*(?:\[\d+\]\s*)+"` instead of matching a single `(\[\d+\])?` as in [Issue #573](https://github.com/stanford-oval/storm/issues/573) — accessed 2026-11-09) and parse Markdown headings with `re.match(r"^(#+)\s+(.*)$", line)` instead of `line.count("#")` ([Issue #581](https://github.com/stanford-oval/storm/issues/581) — accessed 2026-11-09).

### 6.4 Borrow from `Alibaba-NLP/DeepResearch` & `MiroMindAI/MiroThinker`: Hybrid Context Management (Markovian `Report` + `keep_tool_result: 5` + Lexicon Anchor)
- **Source:** [`WebAgent/WebResearcher/README.md`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/WebAgent/WebResearcher/README.md), [`inference/tool_visit.py`](https://github.com/Alibaba-NLP/DeepResearch/blob/main/inference/tool_visit.py), and [`apps/miroflow-agent/src/llm/base_client.py`](https://github.com/MiroMindAI/MiroThinker/blob/main/apps/miroflow-agent/src/llm/base_client.py) — accessed 2026-11-09.
- **How It Improves Our System:**
  - Combine **MiroThinker's `keep_tool_result: 5`** (retaining full raw tool outputs for the last 5 tool calls while keeping all assistant reasoning/tool-call history) with **WebResearcher's periodic evolving `Report` state** every 10–15 turns.
  - Use **Tongyi's goal-conditioned visit extraction (`visit(url, goal)`)** so raw 50K-token web pages are distilled into `{rational, verbatim_evidence, summary}` before entering the main agent context.
  - Enforce **MiroThinker's 300-turn hard ceiling** ([Issue #137](https://github.com/MiroMindAI/MiroThinker/issues/137) — accessed 2026-11-09) and **what we avoid from `AI-Scientist-v2` ([Issue #100](https://github.com/SakanaAI/AI-Scientist-v2/issues/100) & [Issue #127](https://github.com/SakanaAI/AI-Scientist-v2/issues/127) — accessed 2026-11-09)**: persist checkpoint summaries immediately after every phase transition and validate that required domain terms + verified `[URL]` citations from the initial plan are preserved across every compression boundary (preventing "ghost lexicon decay").

### 6.5 Borrow from `RUC-NLPIR/WebThinker` & `TIGER-AI-Lab/OpenResearcher`: External Draft Buffer with Outline-Only Check + Cursor Line-Range Citations
- **Source:** [`scripts/prompts/prompts_report.py`](https://github.com/RUC-NLPIR/WebThinker/blob/main/scripts/prompts/prompts_report.py) (`<|begin_check_article|>`) and [`TIGER-AI-Lab/OpenResearcher/browser.py`](https://github.com/TIGER-AI-Lab/OpenResearcher/blob/main/browser.py) — accessed 2026-11-09.
- **How It Improves Our System:** Write report sections to an external file buffer while providing a lightweight `check_article_outline` tool that returns only H1–H3 headings and citation counts per section to the orchestrator. When inspecting local or cached sources, expose stateful `open(cursor, loc, num_lines)` and `find(pattern, cursor)` viewport tools with exact line provenance (`[cursor†Lstart-Lend]`).

### 6.6 Borrow from `SakanaAI/AI-Scientist-v2`: Runtime Data-Schema Manifests + VLM Visual-Text Consistency Gate
- **Source:** [`SakanaAI/AI-Scientist-v2` Issue #126](https://github.com/SakanaAI/AI-Scientist-v2/issues/126) & [`ai_scientist/perform_vlm_review.py`](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/ai_scientist/perform_vlm_review.py) — accessed 2026-11-09.
- **How It Improves Our System:** Whenever an agent aggregates structured data or plots across subagent outputs, automatically introspect and inject a **deterministic runtime schema manifest** (keys, types, shapes, row counts) into the prompt ([Issue #126](https://github.com/SakanaAI/AI-Scientist-v2/issues/126) proved this raised plot generation success from 0% across 5 retries to 100% on attempt 1). Additionally, run a final automated **NeurIPS/VLM consistency review** checking that every table/figure caption and cross-reference matches the main text—with strict fail-loud assertions if the reviewer model fails to run ([Issue #133](https://github.com/SakanaAI/AI-Scientist-v2/issues/133) — accessed 2026-11-09).

### 6.7 Borrow from `Alibaba-NLP/DeepResearch` Issue #251: Search-Time Benchmark Decontamination Guardrails
- **Source:** [`Alibaba-NLP/DeepResearch` Issue #251](https://github.com/Alibaba-NLP/DeepResearch/issues/251) & [`RUC-NLPIR/WebThinker` Issue #32](https://github.com/RUC-NLPIR/WebThinker/issues/32) — accessed 2026-11-09.
- **How It Improves Our Benchmark Harness:** In our `research-method-benchmarking` evaluation harness, enforce a **search-time domain/query decontamination filter** (blocking benchmark host repositories, HuggingFace dataset mirrors, and exact verbatim >12-word query matches against benchmark prompts) so we measure genuine research methodology rather than accidental retrieval of leaked benchmark ground truth.
