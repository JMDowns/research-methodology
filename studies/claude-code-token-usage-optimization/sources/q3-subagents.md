# Q3 — Subagents: overhead, multipliers, model choice, result collection, handoff

## Short answers

1. **Fixed overhead.** Official docs give no token count for a subagent's fixed overhead. They do say what it contains: its own system prompt plus environment details (not the Claude Code system prompt), the delegation prompt, the full CLAUDE.md hierarchy (Explore and Plan skip it), a git status snapshot, and inherited built-in and MCP tools. A non-fork subagent has its own cache and does not read the parent's, so its first request is uncached. It then gets only a 5-minute TTL by default, even on a subscription. Docs say use the main conversation for quick targeted changes, shared-context phases, and latency-sensitive work. Use subagents for verbose output, tool restrictions, and self-contained work that returns a summary. A fork shares the parent's cache and is cheaper than a fresh subagent when it needs the same context. "Inline is cheaper" is therefore the docs' stance for small tasks, but there is no break-even number anywhere (unverified, not published).
2. **Multipliers.** Anthropic: agents use about 4x the tokens of chat, multi-agent about 15x. Token use alone explained 80% of BrowseComp variance. Opus lead + Sonnet subagents beat single-agent Opus by 90.2% on an internal research eval. Anthropic says it only pays for high-value, heavily parallel tasks, and is a poor fit for work needing shared context (coding named as an example). The Claude Code docs say agent teams use roughly 7x a standard session. Caveat: these are research-task numbers, not coding.
3. **Sonnet/Haiku vs Opus.** Anthropic's own Sonnet 5.5 launch page shows Sonnet 5.5 close to Opus 5.5 on agentic coding (Terminal-Bench 4.0 70.6 vs 66.4; CursorBench 4.0 55.5 vs 57.8; FrontierCode 1.1 52.1 vs 54.4) at half the price ($2/$10 vs $4/$20 per M tokens; cache read $0.10 vs $0.20). No controlled study of mechanical subagent work (edits, test runs, triage) was found. Practitioner reports are anecdotal. Haiku is reported weaker on coding (blogs, unverified). Setting the model: all four mechanisms exist (see below).
4. **Collecting many results.** Official facts: a background subagent's result arrives as a completion notification in a later turn. The main thread does not process it until it takes a turn. The docs describe no batching or coalescing of notifications (not found; open question). The documented ways to avoid waking the orchestrator per agent are (a) dynamic workflows, where intermediate results stay in script variables and only the final answer reaches Claude's context, (b) subagents that write results to files and return only a short reference (Anthropic multi-agent post), (c) a fan-out agent that aggregates sibling results before reporting.
5. **Handoff/restart.** Resume with SendMessage (keeps the full history and can read the original run's cache if still warm), but the history keeps growing. Cheaper restart: fresh subagent with a short brief plus a state/summary file. Anthropic's pattern: summarize completed phases to external memory, spawn fresh subagents with clean contexts. Subagents also support auto-compaction and a per-agent `autoCompactWindow` (100000 to 1000000) in frontmatter.

## Evidence

### Q3.1 Overhead and when inline wins
- Context a subagent starts with (system prompt, task message, CLAUDE.md, git status, tools); "Each subagent starts with a fresh, isolated context window"; descriptions of non-built-in subagents cost context, warning at 15,000 tokens. [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — accessed 2026-11-07
- Subagents vs main conversation: main conversation for back-and-forth, shared-context phases, quick targeted change, latency ("A subagent that isn't a fork starts fresh and may need time to gather context"). Subagents for verbose output, tool restrictions, self-contained work. Warning: "Running many subagents that each return detailed results can consume significant context, and each subagent spends tokens of its own". [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — accessed 2026-11-07
- Cache: "Its first request doesn't read the parent's cache, because the two prefixes differ"; subagents "get five minutes even on a subscription" unless set (`subagentPromptCacheTtl` / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`, v2.1.242+). Forks inherit prefix and read the parent's cache. Resumed subagents can read the cache the original run warmed. [How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching) — accessed 2026-11-07
- Fork "costs less than a fresh subagent for tasks that need the same context"; a fork can't spawn forks; fork mode on by default since v2.1.302 (and then Claude can't "wait" for a subagent). [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — accessed 2026-11-07
- Anthropic blog: subagents "worth that cost when context isolation, parallelism, or a fresh perspective actually helps"; skip for small tasks, sequential dependent work, same-file edits; rule of thumb 10+ files or 3+ independent pieces. No token figures. [How and when to use subagents](https://claude.com/blog/how-and-when-to-use-subagents-in-claude-code) — accessed 2026-11-07
- Delegating verbose ops (tests, logs, docs) keeps output out of main context; "The subagent's own requests still draw on your usage." [Manage costs](https://code.claude.com/docs/en/costs) — accessed 2026-11-07
- Plan usage `/usage` shows attribution of usage to skills, subagents, plugins, MCP servers. `Prompt cache (main)` line covers main conversation only, not subagents. [Manage costs](https://code.claude.com/docs/en/costs) — accessed 2026-11-07

### Q3.2 Multipliers
- "agents typically use about 4x more tokens than chat interactions... multi-agent systems use about 15x"; three factors explain 95% of BrowseComp variance, tokens alone 80%; Opus 4 lead + Sonnet 4 subagents beat single-agent Opus 4 by 90.2%; poor fit "domains that require all agents to share the same context", most coding has fewer parallelizable tasks; effort-scaling rules (1 agent 3-10 calls for simple fact finding, 2-4 subagents for comparisons, 10+ for complex); vague briefs caused duplicate work (need objective, output format, tool guidance, boundaries). [Anthropic: How we built our multi-agent research system](https://www.anthropic.com/engineering/built-multi-agent-research-system) — accessed 2026-11-07 (same article also fetched at /engineering/multi-agent-research-system, same content)
- Cross-check on a second domain: 4x / 15x and 90.2% reported by [Simon Willison's blog summary](https://simonwillison.net/2025/Jun/14/multi-agent-research-system/) — accessed 2026-11-07 (via search snippet, page not fetched).
- Agent teams: "approximately 7x more tokens than standard sessions when teammates run in plan mode". Use Sonnet for teammates, keep teams small. [Manage costs](https://code.claude.com/docs/en/costs) — accessed 2026-11-07
- Workflows: "a single run can use meaningfully more tokens than working through the same task in conversation"; warning at more than 25 agents or projected 1.5M tokens. [Dynamic workflows](https://code.claude.com/docs/en/workflows) — accessed 2026-11-07
- Not found: any measured multiplier for coding subagents.

### Q3.3 Model quality and how to set the model
- Sonnet 5.5 vs Opus 5.5 benchmark table and prices (Sonnet $2 in / $10 out; Opus $4 / $20; cache read $0.10 vs $0.20). Page says Sonnet 5.5 "complements Opus 5.5 best when running at lower effort settings". Footnote: at Max effort Sonnet 5.5 more often ran the code-review skill that fans out to many subagents, causing timeouts or out-of-scope edits on two FrontierCode tasks. A developer quote: confident letting Sonnet 5.5 implement once Opus sets architecture. [Anthropic: Claude Sonnet 5.5](https://www.anthropic.com/news/claude-sonnet-5-5) — accessed 2026-11-07. Only one source for the table (page read through the fetch tool's summarizer; numbers worth a second look before quoting). Note: the fetch said it did not report SWE-bench.
- Practitioner/blog claims (low reliability, self-reported): Sonnet vs Opus gap about 3-4x cost with similar output on most implementation tasks; Opus clearly better on architecture (88% vs 65% in one blog's table); Haiku fine for well-defined repetitive work, limited coding ability; Reddit users have Opus orchestrate Haiku/Sonnet subagents for search and mechanical migrations. Seen only as search snippets, not fetched: [DEV: Pick the right Claude Code model](https://dev.to/klement_gunndu/pick-the-right-claude-code-model-for-every-task-1p6a), [Claude Tips: subagent model savings](https://claude-tips.pages.dev/tips/subagent-model-cost-savings), [claudefa.st Sonnet 5 vs Opus 4.8](https://claudefa.st/blog/models/claude-sonnet-5-vs-opus-4-8) — accessed 2026-11-07. (unverified)
- No controlled study of Sonnet vs Opus on mechanical agentic subtasks found.
- **Setting the model (verified in docs):**
  - Agent tool call `model` parameter: aliases `sonnet`, `opus`, `haiku`, `fable` only (no full ID, no `inherit`).
  - Agent frontmatter `model:` accepts alias, full ID, or `inherit`.
  - `CLAUDE_CODE_SUBAGENT_MODEL` exists. Since v2.1.251 it is a default only. Order: per-call parameter, then frontmatter, then this variable, then the main model. Before v2.1.251 it overrode everything. To force one model for all subagents also set `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`. By itself it does not change built-in Explore and Plan.
  - Explore is NOT Haiku by default: it uses the main conversation's model (Opus on subscription). To run it on Haiku, define a user/project subagent named `Explore` with `model: haiku`. claude-code-guide is Haiku, statusline-setup is Sonnet.
  - Workflow agents follow the same order; a script can name a model per stage.
  - `opusplan`: Opus in plan mode, Sonnet in execution, but each toggle is a model switch with a fresh cache.
  - [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — accessed 2026-11-07; cross-check: [Model configuration](https://code.claude.com/docs/en/model-config) (lists the Agent `model` parameter, frontmatter and `CLAUDE_CODE_SUBAGENT_MODEL` as subagent model controls; same domain) — accessed 2026-11-07; [Manage costs](https://code.claude.com/docs/en/costs) — accessed 2026-11-07
  - Each model has its own cache; a fresh subagent on a different model has no cache anyway, so Sonnet for a fresh subagent loses nothing on cache. Switching the MAIN thread's model mid-session does lose it. [Prompt caching](https://code.claude.com/docs/en/prompt-caching) — accessed 2026-11-07

### Q3.4 Collecting many background results
- "A background subagent's results reach Claude as a completion notification in a later turn. Claude waits for that notification before reporting"; marked as an automated event. Default: subagents spawned from the main conversation start in the background. [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — accessed 2026-11-07
- Each notification starts a main-thread turn that re-sends the full context (docs list the analogous idle triggers: scheduled tasks, cross-session messages, goal check-ins "sending your full context each time"). [Manage costs](https://code.claude.com/docs/en/costs) — accessed 2026-11-07. The docs do not list subagent notifications in that list and say nothing about coalescing.
- Workflows: with subagents/skills/teams "every result goes into a context window"; a workflow script "holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer". Scale "dozens to hundreds of agents per run", up to 16 concurrent by default, 1,000 per run, `agent()` accepts a JSON `schema` for structured results; same-prefix siblings share cache (first agent held 5 s so others read its cache). Resumable in session. [Dynamic workflows](https://code.claude.com/docs/en/workflows) — accessed 2026-11-07
- Anthropic's research system: subagents "store their work in external systems" and "pass lightweight references back to the coordinator" to avoid the "telephone game" and token overhead. [Anthropic multi-agent post](https://www.anthropic.com/engineering/built-multi-agent-research-system) — accessed 2026-11-07
- Anthropic blog warns a relay of subagents passing state through files is worse than one session for sequential work. [How and when to use subagents](https://claude.com/blog/how-and-when-to-use-subagents-in-claude-code) — accessed 2026-11-07
- Concurrency limit default 20 subagents (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`); `CLAUDE_CODE_FORK_SUBAGENT=0` lets Claude wait for a subagent. [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — accessed 2026-11-07
- Unverified (search snippets only): third-party page claims notifications are held until the parent's turn boundary and a queue drops oldest low-priority items past 50 pending. Not confirmed by official docs.

### Q3.5 Handoff / continuation
- Resume: "Resumed subagents retain their full conversation history"; via SendMessage; Explore/Plan one-shot and not resumable; transcripts in `~/.claude/projects/{project}/{sessionId}/subagents/agent-{id}.jsonl`, kept 30 days (`cleanupPeriodDays`). Names survive restart only since last compaction; use agent ID. [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — accessed 2026-11-07
- A resumed run's first request can read the original run's cache if within TTL (5 min default for subagents) — so resume right away, or set `subagentPromptCacheTtl=1h`. [Prompt caching](https://code.claude.com/docs/en/prompt-caching) — accessed 2026-11-07
- Auto-compaction applies to subagents; `autoCompactWindow` frontmatter (100000-1000000, plain integer, v2.1.296+) makes one subagent compact earlier; `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` also applies. [Create custom subagents](https://code.claude.com/docs/en/sub-agents) — accessed 2026-11-07
- Anthropic: agents "summarize completed work phases and store essential information in external memory"; near limits "spawn fresh subagents with clean contexts" with careful handoffs. [Anthropic multi-agent post](https://www.anthropic.com/engineering/built-multi-agent-research-system) — accessed 2026-11-07
- Workflow resume: completed agents return saved results; a failed agent causes it and all later agents to rerun. Stalled agents auto-restart from the same prompt without the old transcript (up to 5 restarts). [Dynamic workflows](https://code.claude.com/docs/en/workflows) — accessed 2026-11-07

## Implications for the owner's local data (my reading, not sourced)
- Local: 283 subagents, median 65 turns, median per-agent cache read 6.6M, 9 on Sonnet. Per the docs, each subagent request counts against plan usage, and subagents sit on a 5-minute TTL, so any pause above 5 min inside a long agent causes a full rewrite. Setting `subagentPromptCacheTtl=1h` costs more per write but may help long agents (untested).
- Quickest levers that docs support: pass `model: "sonnet"` per call for mechanical jobs; define project agents with `model: sonnet`; define an `Explore` override with `model: haiku`; use `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` as a default (does not override explicit choices since v2.1.251); for recurring "cycle" jobs consider saved workflows so results stay out of the orchestrator.
